# MahoCrawl Development and Build Guide

[日本語](DEVELOPMENT.md) | English

This guide explains how to build and develop MahoCrawl from source. If you only want to use the app, download a prebuilt app by following the [README](../README.en.md).

## Architecture

MahoCrawl is a macOS and Windows app that calls SiteOne Crawler v2.5.1 through a secure Tauri v2 bridge. The UI is built with Vue 3 + TypeScript + Vite.

- `src/`: Vue 3 UI, settings CRUD, gallery, logs, and frontend validation
- `src-tauri/src/lib.rs`: settings persistence, input validation, restricted SiteOne commands, sidecar process state, event delivery, and capture enumeration
- `src-tauri/src/platform.rs`: OS-specific behavior such as the home directory, sidecar names, and starting/stopping child processes
- `src-tauri/binaries/`: macOS (arm64 / x86_64) and Windows (x86_64) SiteOne Crawler binaries following the Tauri externalBin naming convention (generated by `npm run build:siteone`; not tracked by Git)
- `patches/`: custom patches for SiteOne Crawler / chromiumoxide
- `Resources/Licenses/`: the bundled SiteOne Crawler license and the third-party license list
- `scripts/`: helper scripts for building SiteOne, generating the license list, building releases, and more
- `docs/design/maho-crawl-tauri-concept.png`: the reference for layout and color scheme

The frontend cannot run arbitrary shell commands. Launching the sidecar is limited to the Rust `start_crawl` command, and arguments are passed as a `Vec<String>`. Stopping a crawl and opening reports, output folders, or source images are also handled as Rust commands with individual arguments.

The Rust bridge re-validates the URL, depth, workers, request rate, timeout, output folder, and capture size dimensions/IDs/duplicates. Settings are stored in Tauri's app config directory, with localStorage as a fallback in the browser.

## Requirements

- macOS 13 or later
- Node.js
- Rust (installed via rustup; Homebrew's Rust does not include the x86_64 standard library, so the Intel build fails with it)
- [cargo-about](https://github.com/EmbarkStudios/cargo-about) (used to generate the third-party license list)

```bash
rustup target add aarch64-apple-darwin x86_64-apple-darwin
cargo install cargo-about --locked --features cli
```

If Homebrew's `cargo` comes first in your PATH, run `export PATH="$HOME/.cargo/bin:$PATH"` before building.

## Setup

The SiteOne Crawler binaries are not included in the repository, so generate the custom build first (this takes a few minutes).

```bash
npm install
npm run build:siteone
```

## Development and testing

```bash
npm run dev
npm run test
npm run build
cargo test --manifest-path src-tauri/Cargo.toml
cargo check --manifest-path src-tauri/Cargo.toml
npm run tauri dev
```

`npm run dev` starts a UI preview in the browser using sample data. Actual crawls run in the desktop app started with `npm run tauri dev`.

To create a debug bundle of the Tauri app:

```bash
npm run tauri build -- --debug
```

## Building the app

To create a local release build (for the architecture of the Mac you are running on):

```bash
npm run build:app
```

`build:app` regenerates the third-party license list (`Resources/Licenses/THIRD_PARTY_LICENSES.txt`) and then builds the app. Rust build artifacts are built with `--remap-path-prefix` so that local absolute paths are not left in them.

After a successful build, `src-tauri/target/release/bundle/macos/MahoCrawl.app` is automatically copied to `release/MahoCrawl.app` in the project root. On later builds, the previous app is replaced after the copy completes. `release/` is not tracked by Git.

`npm run build` builds only the frontend, and `npm run tauri build` builds to Tauri's default output location.

## Releasing

To create the zip files for GitHub Releases, run the following. It builds the Apple Silicon and Intel versions separately and outputs `release/MahoCrawl_<version>_aarch64.zip` and `release/MahoCrawl_<version>_x86_64.zip`.

```bash
npm run build:release
```

The macOS app is ad-hoc signed (`signingIdentity: "-"` in `tauri.conf.json`), but it is not signed with a Developer ID or notarized.

The Windows version (NSIS installer) is built with GitHub Actions (`.github/workflows/windows.yml`). Pushing a `v*` tag builds SiteOne Crawler and the app on Windows and attaches `MahoCrawl_<version>_x64-setup.exe` to the GitHub Release (a draft release is created if none exists). When you run the workflow manually from the Actions page, you can download the installer from its Artifacts.

The release steps are:

1. Update the version in `package.json`, `src-tauri/tauri.conf.json`, and `src-tauri/Cargo.toml`, then commit and push.
2. Create and push a tag (this starts the Windows build).
3. Create the macOS zip files with `npm run build:release` and attach them to the release.
4. After the Windows installer is attached, write the release notes and publish the release.

```bash
git tag v<version>
git push origin v<version>
npm run build:release
gh release upload v<version> release/MahoCrawl_<version>_aarch64.zip release/MahoCrawl_<version>_x86_64.zip
```

If the Windows build created the release as a draft, publish it with `gh release edit v<version> --draft=false`.

### Developer ID signing and notarization

To distribute an app signed with a Developer ID and notarized, sign it with the hardened runtime enabled and then notarize it.

```bash
npm run build:app
(cd src-tauri/binaries && shasum -a 256 -c ../../Resources/Binaries/checksums.sha256)
codesign --force --options runtime --deep --sign "Developer ID Application: <Your Name>" release/MahoCrawl.app
xcrun notarytool submit release/MahoCrawl.app --keychain-profile "<profile>" --wait
xcrun stapler staple release/MahoCrawl.app
```

## Custom build of SiteOne Crawler

MahoCrawl bundles an unofficial custom build based on SiteOne Crawler v2.5.1. It includes the following changes:

- When capturing with a browser, Basic authentication credentials are sent only to the origin that exactly matches the target URL.
- `--http-auth-stdin` reads credentials from standard input (they are never passed as command-line arguments).

To regenerate the custom build:

```bash
npm run build:siteone
```

The patches are in `patches/`. The source versions and SHA-256 checksums are written to `Resources/Binaries/` during the build (not tracked by Git, like the binaries).
You can specify the upstream source commit SHAs with the `SITEONE_COMMIT` and `CHROMIUMOXIDE_COMMIT` environment variables. The defaults are recorded in the script, and the SHAs are verified after fetching to protect against supply chain risks from retagging.

Tauri externalBin uses the following target names:

- `siteone-crawler-aarch64-apple-darwin`
- `siteone-crawler-x86_64-apple-darwin`
- `siteone-crawler-x86_64-pc-windows-msvc.exe`

By default, the build targets Apple Silicon and Intel on macOS, and x86_64 on Windows (Git Bash). You can change this with the `SITEONE_TARGETS` environment variable (space-separated).

On Windows, stopping a crawl ends SiteOne Crawler and its child processes (such as Chrome) together with `taskkill /T /F`. On macOS, SIGINT is sent to the process group, followed by SIGKILL if it does not exit.

After updating, run `siteone-crawler-* --version`, `cargo test`, `npm run build`, and `cargo check`. MahoCrawl never passes custom flags that do not exist in the SiteOne CLI. Because the current v2.5.1 has no CLI flag dedicated to cookie banners, the setting value is saved, but the UI marks it as "currently unsupported" (「現在未対応」) and disables the control.

You can verify the stdin authentication of the custom SiteOne build locally with `scripts/test-siteone-auth-integration.sh`.

## Output structure details

Each capture size receives its own writable `.siteone-http-cache` through the argument array, which avoids cache conflicts between sizes. The internal cache is a hidden directory excluded from gallery enumeration and is deleted on a best-effort basis after the sidecar exits.

Size names are converted to safe slugs and always include the dimensions as a suffix. If a run folder or size folder already exists, a suffix is added to avoid overwriting it.

## Licenses

For third-party licenses, see `Resources/Licenses/THIRD_PARTY_NOTICES.txt` and `Resources/Licenses/THIRD_PARTY_LICENSES.txt`. After updating dependencies, regenerate the list with `npm run licenses`.
